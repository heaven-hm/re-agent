# REA Engine tool distribution and integration gap audit

**Scope:** checked-in `third_party/`, declared npm package payload, tool bootstrap and discovery code, provider composition, and available license/provenance records in this worktree on 2026-10-14. This is a repository inspection, not a legal opinion, a cross-platform installation test, or proof that all advertised tools work. The checkout has unrelated uncommitted changes; findings about recently changed files describe this worktree and should be rechecked against the commit before release.

## Finding

REA Engine is a host application with optional providers and externally supplied analysis tools. It is not currently a self-contained distribution of the full open-source reverse-engineering stack, nor a universal desktop/game reverse-engineering engine. The repo contains some upstream source, one managed-tool package, a separately published Ghidra release asset, and scripts for a Python-tool bundle whose own manifest explicitly denies public redistribution approval. Many tools are only discovered or documented; tool discovery does not wire them into target analysis.

The most important distribution limitation is explicit in [the tool bootstrap guide](../../autonomy-tool-bootstrap.md#L48-L68): the Python bundle targets macOS ARM64/Python 3.12, omits angr, and sets `publicRedistributionApproved: false` because source and notice coverage for embedded native dependencies is unresolved. The guide also says it does not supply every analysis, game, graphics, or platform integration.

### Repository payload is selective

`package.json#files` is an explicit selective allow-list, not a vendoring rule. It includes ILSpy/libgdiplus metadata, license and notice files, and the Ghidra manifest directory; it excludes the ILSpy package, libgdiplus binaries/source archive, Ghidra release archive, and all unapproved tool binaries. It also does not include every source submodule (`binwalk`, `unblob`, `jadx-headless-mcp`, `wakaru`, `ghidra-nativeaot`) or all optional tool binaries. See [`package.json`](../../../package.json#L46-L121). `.gitmodules` declares source submodules rather than executable installations ([`.gitmodules`](../../../.gitmodules)). A shallow clone without submodule initialization omits those source trees.

The generated Python bundle is an optional local artifact, not a shippable default: its builder requires macOS ARM64 and Python 3.12 ([`scripts/package-autonomy-tool-bundle.mjs`](../../../scripts/package-autonomy-tool-bundle.mjs#L8-L34), [bootstrap guide](../../autonomy-tool-bootstrap.md#L48-L62)). It records unapproved redistribution rather than silently publishing an incomplete bundle. This is the correct current behavior until the dependency and notice audit is complete.

## License and provenance gaps

1. **Python/native dependency coverage remains unresolved.** The bootstrap bundle itself marks public redistribution false and says the Frida/LIEF embedded native-source completeness is not proven ([`scripts/package-autonomy-tool-bundle.mjs`](../../../scripts/package-autonomy-tool-bundle.mjs#L30-L34), [`docs/autonomy-tool-bootstrap.md`](../../autonomy-tool-bootstrap.md#L58-L62)). Do not publish its archive as an approved bundle yet.
2. **ILSpy transitive notices are called incomplete.** The bundled ILSpy README says they are still being collected ([`third_party/ilspy/README.md`](../../../third_party/ilspy/README.md#L1-L9)); a root MIT license alone is insufficient to call the package dependency graph fully audited.
3. **Ghidra's top-level records do not replace component notices.** The root notice explicitly says Ghidra contains additional module licenses and GPL support programs, and top-level copied documents are not a complete distribution record ([`THIRD_PARTY_NOTICES.md`](../../../THIRD_PARTY_NOTICES.md#L76-L82)). Preserve and verify the exact archived distribution's embedded notices on release.
4. **Submodule availability and redistribution are different.** `third_party/README.md` states the engines are separately supplied and source submodules are not in the npm package ([`THIRD_PARTY_NOTICES.md`](../../../THIRD_PARTY_NOTICES.md#L51-L53)). Submodule presence should not be counted as an installed binary.
5. **Tool notices are not a full legal review of target assets or OS packages.** Root notices say separately installed tools carry their own terms and OS/agent dependencies are not all inventoried ([`THIRD_PARTY_NOTICES.md`](../../../THIRD_PARTY_NOTICES.md#L104-L134)). Any game-data, capture SDK, debugger plugin, or packaged OS-runtime bundle needs its own provenance and license audit.
6. **No evidence supports “all best tools bundled.”** Current documentation explicitly distinguishes installed tools from distributed tools and says the clone does not contain every installed external tool ([`README.md`](../../../README.md#L154-L156)). The present package is an engine package plus selected optional artifacts, not an all-tools image.

## Highest-value implementation sequence

1. **Make distribution inventory machine-checkable.** Produce one table/manifest of every candidate with source, version, exact artifact hash, SPDX expression, dependency/notice status, supported OS/architecture, bundle status, adapter status, and proof link. Fail packaging if an artifact is marked distributable without complete required notice/provenance fields.
2. **Close current licensing gates before adding more binaries.** Finish the Frida/LIEF native component audit and ILSpy dependency notices, then run a release-package unpack audit. Keep unreviewed optional tools external.
3. **Extend provider coverage from inventory to behavior.** Bounded radare2 function inventory and address-bound disassembly are wired through provider, CLI and MCP. The next provider check is a successful real-host disassembly run with confirmed cleanup; CFG/call-reference evidence and a Frida observation correlated to the same target hash/function address remain future work. Health detection alone remains `available`, not `integrated`.
4. **Add native app interaction per OS.** Implement shared operations with real Windows and Linux providers and a real worker lane; record OS-specific capability absence instead of implying portability.
5. **Build a narrow game evidence path.** Start with licensed synthetic or user-authorized games; capture deterministic input/tick/frame traces and state comparisons. Add RenderDoc only when capture is validated on the relevant OS/GPU, rather than counting its executable as a game reverse-engineering integration.
6. **Publish only reproducible profiles.** Separate core engine, optional signed/checksummed tool packs, and proprietary BYO adapters. Maintain a tested install profile and notice manifest per platform. Do not claim byte-identical executables: independent executable bytes are expected to differ; report exact equality only for the specified observable evidence (or identical hashes where the binaries themselves are equal).

## Audit conclusion

The repository has a substantial, evidence-oriented REA engine and multiple real provider integrations, but its current state does **not** satisfy a request to bundle all redistributable static, runtime, desktop-control, browser and game-analysis tools across major operating systems. Important tools are BYO or merely detected; some packaged artifacts are platform-specific; and at least two material license/dependency audits are explicitly unfinished. The repo should not be described as a complete universal engine or as proving byte-identical reconstruction of arbitrary closed-source apps or games.
